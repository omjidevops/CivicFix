Chapter 1: Background

The Civic Governance Crisis: Why We Need CivicFix

🏛️ Opaque Bureaucracy
  • Citizens lodge complaints into an administrative "black hole".
  • Zero visibility into assigned department, contractor, or officer.
  • No guaranteed resolution deadlines or SLA enforcement for taxpayers.
  • Citizens become disillusioned and stop reporting civic hazards.
🔄 Duplicate & Spam Overload
  • Multiple residents report the exact same road pothole or water leak.
  • Field departments are overwhelmed with 10+ identical tickets for 1 issue.
  • Wastes municipal inspection budget, fuel, and triage manpower.
  • No spatial clustering to aggregate neighborhood complaints.
⏳ FIFO Queue & Ghost Closures
  • First-In-First-Out: Live electrical sparking wires wait behind lawn mowing.
  • Zero algorithmic urgency prioritization for life-safety hazards.
  • Contractors mark tickets "Resolved" on paper without visiting sites.
  • No photographic proof or citizen satisfaction confirmation loop.

Chapter 3: Architecture

End-to-End Enterprise System Architecture

Layer 1: Client Tier (Single Page Application) React 18.3 • Vite 5.4 • Leaflet 1.9 • Axios

Responsive UI, interactive OpenStreetMap cartography, debounced duplicate checks, and automated Bearer token injection via Axios interceptors.

Layer 2: Security & Gateway Tier (Stateless Auth) Spring Security 6 • JWT HMAC-SHA256 • BCrypt • CORS

Extracts Bearer token, validates cryptographic signature & expiration, populates SecurityContextHolder with authorities, and enforces method-level RBAC.

Layer 3: Business & Service Tier (Domain Logic) Spring Boot 3.4.3 • REST Controllers • @Transactional Services

REST Controllers exposing JSON endpoints. Specialized business services encapsulating Haversine duplicate detection, dynamic priority calculation, and reputation auditing.

Layer 4: Data Persistence Tier (ACID Storage) Spring Data JPA • Hibernate ORM • HikariCP • MySQL 8.0

10 relational tables in 3NF, composite spatial B-Tree indexing on (lat, lon, status, category), and declarative transaction rollbacks on failure.

Smart Algorithm 1: Dynamic Priority Scoring Engine

Priority Score (P) = S_base + V_boost + A_escalation + K_bonus ∈ [0.0, 100.0]
S_base
Base Severity
Severity × 15.0
Range: [15.0 – 75.0]

Derived directly from user/admin rating (1 to 5) reflecting physical hazard scale.

V_boost
Community Votes
min(Votes × 2.0, 10.0)
Range: [0.0 – 10.0]

Crowdsourced democratic upvoting by verified local residents amplifies urgency.

A_escalation
Aging Escalation
min(Days × 1.0, 10.0)
Range: [0.0 – 10.0]

Increases 1 point per day unsolved. Guarantees neglected tickets bubble up.

K_bonus
Hazard Keywords
+5.0 if matched
Range: [0.0 or 5.0]

Scans text for: "spark", "collapse", "danger", "fire", "burst", "overflow".

Chapter 3: Algorithms

Smart Algorithm 2: Geospatial Duplicate Detection

📐 Two-Stage Algorithmic Logic
  • Stage 1: Radius Pre-Filtering (d ≤ 150m): Bounding box query retrieves all active complaints in the same category within 150 meters.
  • Stage 2A: Immediate Proximity (d ≤ 40m): If within 40m in the same category (e.g. same intersection), instantly flagged as duplicate.
  • Stage 2B: Semantic Similarity (40m < d ≤ 150m): Computes Jaccard Token Similarity between titles and descriptions: J(A, B) = |A ∩ B| / |A ∪ B|. If J > 0.25, flagged as duplicate.
  • Stage 3: Debounced Client Warning: Warns citizen before submission, showing distance, existing ticket ID, and an instant Upvote button.
🧮 Mathematical Formulations
1. Haversine Great-Circle Distance:
a = sin²(Δφ/2) + cos φ₁ · cos φ₂ · sin²(Δλ/2)
d = 2 · R · atan2( √a, √(1−a) )
(Earth radius R = 6,371,000 meters)
2. Jaccard Token Set Similarity:
J(A, B) = |A ∩ B| / |A ∪ B|
Threshold: If J(A, B) > 0.25 (25% word overlap)
and d ≤ 150m => Flag as Duplicate

Chapter 3: Workflows

Audited Complaint Lifecycle State Machine

1. SUBMITTED
Actor: Citizen
GPS coordinates, category, photo & severity logged. Dynamic priority score computed.
2. VERIFIED
Actor: Admin
Admin validates authenticity. Assigns official department & officer with SLA deadline.
3. IN_PROGRESS
Actor: Field Officer
Assigned officer accepts ticket, inspects GPS map, and mobilizes field team on-site.
4. RESOLVED
Actor: Field Officer
MANDATORY: Photo proof & completion remarks must be submitted.
5. CONFIRMED
Actor: Citizen
Reporting citizen verifies resolution quality. +15 civic reputation points awarded.
🛡️ Core Accountability Guarantees & Fraud Prevention
  • No "Ghost" Resolutions: Backend rejects status update to RESOLVED if resolution photo URL or remarks are missing.
  • Closed-Loop Confirmation: Only the citizen who reported the issue (or Admin override) can confirm satisfaction.
  • Immutable Audit Trail: Every transition logs a permanent record to status_history table with timestamps and actor ID.
  • Civic Reputation Engine: Citizens gain +10 for valid reports, +15 for confirming resolution, -20 for abusive spam.

Chapter 4: Data Design

Relational Database Architecture (10 Normalized 3NF Tables)

1. users

Citizens, Employees, Admins with BCrypt salted password hashes & reputation points.

2. departments

Municipal administrative units (Roads, Water Works, Sanitation, Power, Parks).

3. complaints

Core grievance entity with GPS lat/lon, severity, priority score, and SLA status.

4. complaint_media

Original photographic attachments and officer resolution proof images.

5. comments

Two-way citizen-officer discussion thread per ticket with timestamps.

6. votes

Crowdsourced upvotes enforcing single vote via composite UNIQUE(user_id, complaint_id).

7. assignments

Official audit trail of department and officer delegations with resolution deadlines.

8. status_history

Immutable chronological state transition ledger with changed_by timestamps.

9. notifications

Real-time alert notifications dispatched to citizens & officers upon ticket updates.

10. reputation_transactions

Itemized credit/debit civic points ledger ensuring transparent gamification.

Relational Schema Strengths: Normalized to 3NF • Composite B-Tree Spatial Indexes on (latitude, longitude, status, category) • Foreign Key Cascades • HikariCP Pool

Chapter 4: Security & Testing

Security Hardening & Automated Test Verification

🔒 Multi-Layer Security Architecture
  • Stateless JWT Authentication: HS256 algorithm with 256-bit secret key and 24-hour expiration token lifespan.
  • BCrypt Password Hashing: Salted hashing with work factor 10 defends against dictionary and rainbow attacks.
  • Role-Based Access Control (RBAC): Enforced via Spring Security hasRole('ADMIN'), hasRole('EMPLOYEE'), hasRole('CITIZEN').
  • SQL Injection & XSS Defense: Parameterized Spring Data JPA criteria and React automatic HTML entity escaping.
  • RFC 7807 Error Envelopes: Centralized @RestControllerAdvice prevents internal stack trace & credential leaks.
